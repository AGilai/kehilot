# Aliyot — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** gabbaim record each service's aliyot, see Noam's recommendation report for any Shabbat or holiday (fed by the
family trees) and print it; the same print helper gives the seating map a phone print.

**Architecture:** the algorithm is the ported engine `server/cloud/aliyot/engine.py` (Noam owns it; keep it verbatim,
see `docs/ALIYOT-UPSTREAM.md`). This plan adds the data around it in the single DynamoDB table — service items, a
last-aliyah summary item and roster items projected from the family trees — the gabbai routes, and the gabbai screens.
A report reads one 12-month date range of services, one summary item and the roster items; never whole family trees.

**Tech Stack:** Python 3 Lambda (`server/cloud/`), DynamoDB, `pyluach` 2.3.0 (vendored); Expo/React Native + web,
`expo-print`/`expo-sharing` (already dependencies).

**Spec:** the owner-approved model in this session (2026-10-28, CTO message "the model, inside our existing single
table"), `docs/ALIYOT-UPSTREAM.md` (engine contract incl. `project_people` kinds), `docs/UX-DESIGN.md` §17 (tree fields
that feed the roster). Gabbai screens: designed in Task 1 (new section after §18) before any client code.

## Global Constraints

- Engine files are not edited here except through the upstream-compare procedure; `tools/aliyot_compare.py` must stay at
  0 mismatches.
- Items (pk `KEHILA#k`): `ALIYAH#<date>#<service>#<minyan>` = `{reading, cancelled, calls:[{position, personId|null, guest?}],
  recordedBy, updatedAt}`; `ALIYOTLAST` = `{personId: {date, reading}}`; `ROSTER#<personId>` = the engine's person dict
  (kind, names, tribe, torah_name, wife_prayer_name, classification, classification_override, hebrew_birth_date,
  bar_mitzvah_date, bar_mitzvah_parasha, yahrzeits, eligible_from, source/daughter flags, active, familyId).
- A service save writes the service item and `ALIYOTLAST` in one transaction; a tree save rewrites that family's
  `ROSTER#` items in one transaction (≤ 100 items; split by family only).
- Report reads: Query `ALIYAH#` between `selected − 13 months` and `selected` (paginated), `ALIYOTLAST`, Query `ROSTER#`.
- Gabbai only (member/listener 403, other Kehila 404). No names in logs; pushes never carry aliyah data.
- Yahrzeit custom is a Kehila setting (`ashkenaz` | `sephardi` | unset), as upstream.
- Invented names only in tests/fixtures. Tests: server suite, `npm test`, `npm run typecheck`, and the compare tool.

## Review Focus

1. Editing or cancelling an old service that was someone's last aliyah — `ALIYOTLAST` equals a full recomputation.
2. A tree edit (father's tribe, a son's birth year, a daughter's marriage) — the son/son-in-law roster rows change
   exactly as upstream `_refresh_roster` would (engine `project_people` kinds).
3. A person removed from a tree but present in old services — history keeps the call (name snapshot), roster drops him.
4. Two gabbaim saving the same service — 409 on the stale version, nothing merged silently.
5. A report for a date 13+ months after the last recorded service, and for Yom Kippur mincha — matches the engine run on
   the full history.

### Task 3: roster projection from family trees

**Files:** create `server/cloud/aliyot/roster.py`; modify `routes_tree.py` (tree PUT also rewrites `ROSTER#` rows of
that family); test `server/tests/cloud/test_aliyot_roster.py`.

**Interfaces — Consumes:** tree `people` (family-tree plan Task 2), engine `project_people` kinds.
**Produces:** `roster_rows(family: dict, members: dict, gabbai_ids: set) -> list[dict]` (engine person dicts).

- [ ] Rules (from `docs/ALIYOT-UPSTREAM.md`): the male adult member → `kind:'self'` (classification default 'א',
  gabbai override kept); each son → `kind:'son'` (father_tribe, father_classification, married, spouse_prayer_name from
  his spouse figure); each married daughter's husband → `kind:'son_in_law'` (daughter_active, daughter_married,
  household_classification); torah_name = the tree's aliyah name; wife_prayer_name = the wife's Mi Sheberach name;
  bar_mitzvah_date/parasha from the stored `barMitzvah`; yahrzeits = deceased figures related to this person
  (father/mother/spouse/son/daughter/father_in_law/mother_in_law) with exact months. Tests first: each kind, a son
  without birth year inactive, the reviewer's two cases, re-projection on tree edits, removal drops rows; then one
  end-to-end test: tree → roster → `engine.recommendations` gives the expected sections. Commit.
