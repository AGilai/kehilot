# The "טכני" (Tech) role — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A fourth Kehila role, stored as `tech` and shown as "טכני", gets the Kehila's configuration and operations
(settings, times, sheet, channels, groups, invites, approvals, hall shape) and never receives personal data about
other people, through any route, export, push, search or cached client data.

**Architecture:** Every authorization decision on the server picks one **named role set** from `server/cloud/authz.py`
(`ALL`, `ADULTS`, `MANAGEMENT`, `GABBAI_ONLY`, …). An AST test fails on any `require(...)` without a named set and on any
role string compared outside `authz.py`, and a table-driven test walks **every** route in `handler.ROUTES` as a tech and
checks the §20.1 result plus a set of secret sentinels that must never appear in a tech's responses. The client mirrors
the sets in `src/client/roles.ts` (with a lint test against role literals) and hides what the server refuses. A tech's
hall editor is a separate, names-free component fed only by seat ids.

**Tech Stack:** Python 3 Lambda (`server/cloud/`, DynamoDB single table, moto + `unittest`), Expo / React Native + web
(`src/`, Node `node --test`, `tsc`), headless Chromium via `~/tools/qa-browser`.

**Spec:** `docs/UX-DESIGN.md` §20 (20.1–20.10, commit b40f1e0), frame `design/mockups/frames/P46.html` (`tech-role.html`).
Also read §18.3 (management), §16.4–16.5 (hall editor), §19.3 (sheet states), §12.6 (role tags). The paused plan
`docs/superpowers/plans/2026-10-28-templates-sheet.md` (Tasks 1–3 done) shares files with this one.

## Global Constraints

- **The principle (§20, binding):** a tech sees names and roles, and never: phones not shown to everyone, families or
  trees of others, children, who sits where (seat names or holders), simchas, aliyot, healing names, private replies.
  A tech is never labelled "גבאי". When in doubt, the narrower set (`GABBAI_ONLY`) wins and the question goes to the
  controller.
- **Owner defaults, pending confirmation (§20.9). Each is exactly one switch**, a module constant in
  `server/cloud/authz.py` mirrored in `src/client/roles.ts` (a test keeps them equal); nothing else may test for them:
  1. `TECH_ACCEPTS_TERMS = False` — only a gabbai accepts the Kehila terms; a tech sees them read-only.
  2. `TECH_REMOVES_OTHERS_MESSAGES = False` — a tech removes only his own messages.
  3. `TECH_IS_MEMBER = True` — a tech is also a full member (family, tree, seat form, phone list as a member).
- **Role sets (server and client use these names only):** `ALL = (listener, member, gabbai, tech)`;
  `NON_LISTENERS = (member, gabbai, tech)`; `ADULTS = NON_LISTENERS if TECH_IS_MEMBER else (member, gabbai)`;
  `MANAGEMENT = (gabbai, tech)`; `GABBAI_ONLY = (gabbai,)`; `LISTENER_ONLY = (listener,)`; `MEMBER_ONLY = (member,)`;
  `APPOINTABLE = (member, tech)` (may be appointed group admin); `TERMS = MANAGEMENT if TECH_ACCEPTS_TERMS else GABBAI_ONLY`.
  "Gabbai-only" anywhere in older plans and comments now means `MANAGEMENT` unless §20.1 marks the thing ✗ for tech.
- **Rules (§20.5):** at least one gabbai always remains (the existing `last_gabbai` witness guard covers becoming tech,
  becoming member, removal, leaving and account deletion). A tech cannot grant the gabbai role and cannot change the
  role of or remove a gabbai: 403 `gabbai_only`. Other fields of a gabbai (classification, groups, tags) a tech may set.
  No invite and no import row ever gives `tech`; a tech's import row with role גבאי is a row problem `gabbai_only`.
  No limit on techs; a tech can be a group admin; a tech's broadcast right is always on and locked.
- **Posts by a tech** are `authorKind: 'management'`, skip the member daily limit, and go on the weekly sheet as
  `state 'in', source 'auto'` (`sheet_rules.initial_state`).
- **Attribution copy (§20.4, §20.7) verbatim.** "צוות הניהול" is the only collective term for gabbaim and techs.

## Review Focus

1. **A gabbai demoted to tech while the app is open.** The open management screens and the on-phone message cache still
   hold gabbai-era data (member phones, families, closed-channel messages). After the role change the client must refetch
   every management screen and wipe the cached messages of channels he can no longer read. Test: Task 6
   `role change gabbai to tech wipes cached closed-channel messages` and Task 7 `management screens remount on role change`.
2. **A tech saves a new hall version for a future Shabbat.** The client cannot send assignments for a tech, so without
   care the new version starts empty and every family loses its seat from that date. The server must carry the base
   version's assignments to seats at the same positions, and refuse (409 `seat_taken`, nothing saved) if any would drop.
   Test: Task 4 `test_tech_new_version_carries_assignments`.
3. **A tech changes the role of a member who has just been made gabbai** (two staff on two phones). The tech's request
   read the old role; the write must fail with 409 `try_again` and never demote the new gabbai. Test: Task 3
   `test_tech_role_change_on_member_who_became_gabbai_meanwhile`.
4. **A pending mazal tov in a closed group channel the tech is not in.** The sheet management list must not hand him the
   message (title, body, family) he cannot read in Messages. Test: Task 2 `test_tech_sheet_skips_unreadable_messages`.
5. **A member link made by a tech who is later set back to member.** Accepting it must answer 410 `invite_expired`, as for
   a demoted gabbai; while he is a tech it must work like a gabbai's link. Test: Task 3
   `test_member_invite_of_demoted_tech_expires`.
