# Kehilot Plan 3: the app Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Move the Expo app (phone and web) onto the cloud API, adding in-app Hebrew/English sign-in through
Cognito, Google and Apple sign-in, Kehila selection, the approved member and gabbai screens, both onboarding
directions (an invite with a role choice, and a list import that pre-creates accounts), and a web deploy to
CloudFront.

**Architecture:** New code sits beside the legacy app; nothing old is rewritten in place. `App.tsx` chooses
the cloud app when `EXPO_PUBLIC_COGNITO_CLIENT_ID` is set, and otherwise the legacy demo (moved, not changed).
The cloud app is built in layers, each testable with `node --test` because none imports `react-native`:
- `src/auth/`: the Cognito JSON API, SRP sign-in and the token manager.
- `src/client/`: the HTTP client, the v2 endpoints, the change-feed poller and the session store.
- `src/i18n/`: the translations and text direction.
- `src/import/`: CSV and XLSX parsing.

React screens in `src/views/` are thin on top of these layers. The backend gains a few routes the app needs,
an import route, and one Cognito-trigger Lambda. Terraform adds CORS, a Cognito domain, OAuth settings on the
app client, and the Google and Apple identity providers.

**Tech Stack:** Expo SDK 57 / React Native 0.86 / react-native-web 0.21, TypeScript 6, `node --test` (Node 22 here,
24 in CI). New packages: `amazon-cognito-identity-js` (SRP only), `expo-auth-session`, `expo-web-browser`,
`expo-crypto`, `expo-font`, `@expo-google-fonts/heebo`, `@expo-google-fonts/noto-serif-hebrew`, `fflate`.
Backend: Python 3.12 Lambdas, boto3, moto. Terraform 1.17.0, AWS provider 6.70.0.

**Spec:** `docs/superpowers/specs/2026-10-26-aws-architecture-design.md`. The sections this plan implements are
§3a, §3b, §4.2, §4.2a, §4.3, §4.5, §4.5b, §4.7, §6 (web deploy and app configuration) and §7.
- UX: `docs/UX-DESIGN.md` and `design/mockups/frames/*.html`. Screen IDs below (M1–M11, GM1–GM6, GD1–GD6)
  are the UX IDs.
- API contract: `server/API.md`, the "v2 (cloud)" section.
- Earlier plans: `docs/superpowers/plans/2026-10-26-foundation-dev-environment.md` and
  `docs/superpowers/plans/2026-10-26-kehila-core-messaging.md`.

**Not in this plan:**
- Plan 2b: family profiles, roster, aliyah, Mi Sheberach and seating on the cloud API, and Person (`P#`) items.
  The import writes profiles and memberships only.
- The day-arc graphic: M1 shows the zmanim as a grid.
- Channel administration screens (GD3); the API and the admin CLI's default channels cover them.

Everything in plan 1's and plan 2a's Global Constraints still applies:
- region `il-central-1`;
- `kehilot-<env>-` names;
- IAM roles with `path = "/kehilot/"` and the `kehilot-boundary` permissions boundary;
- SSM parameters under `/kehilot/<env>/`;
- no PII in logs: never log tokens, emails, names or request bodies;
- ULIDs;
- errors as codes;
- `visibility.py` as the only place that decides visibility;
- commits end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`, on branch `redesign`.

In addition:
- **Terraform: plan → review → the user applies.** Write the change, run `terraform fmt` and `validate`,
  then `plan -out=dev.tfplan`, and read the plan. The executor stops there. The user applies the saved plan.
  Nothing in this plan runs `terraform apply`.
- **No long-lived AWS keys.** Commands here use the `kehilot-deployer` instance role. Google and Apple
  credentials go to SSM `SecureString` parameters, created by the user, never in git.

  user's Mac (`AGENTS.md`: local builds, no EAS Build). This machine runs unit tests, `npm run typecheck`,

- **Expo packages are added with `npx expo install <pkg>`**, which picks the SDK 57 version. Other packages
  are pinned exactly (`npm install --save-exact`).
- **Names in code, fixtures, tests and screenshots are invented** (for example "דנה בדויה", "משפחת בדיוני",

- **Languages (spec §3b):**
  - All new UI text lives in `src/i18n/he.json` and `src/i18n/en.json`, with no literal UI strings in new

  - Hebrew is RTL and English is LTR. Use logical `start`/`end` only. On web, set `document.documentElement`

  - Before sign-in the device language is used (`he` if the device is Hebrew, otherwise `en`). After

  - Content people write is never translated.

  {name}", en "{n} members sent a private blessing to the {name} family".
- **Push payloads stay generic.** The app routes on `data.kehila`, `data.messageId` and `data.screen` only.

## Review Focus

1. **A second person signs in on the same phone or browser** after the first signs out → nothing of the
   first account remains: no messages, no private blessings, no cursor and no Kehila selection. Late
   responses to the first account's requests are dropped. Task 9 (`signOut clears the store and drops late
   responses`).
2. **The user switches Kehila while a `/changes` poll is in flight** → the late page for Kehila A is never
   applied to Kehila B. Task 10 (`late page after a Kehila switch is dropped`).
3. **The ID token expires while the app is in the background**, and on return several requests fail with
   401 at once → exactly one refresh runs and each request is retried once. If the refresh fails, the user
   lands on sign-in, with no refresh loop. Task 6 (`concurrent callers share one refresh`) and Task 7
   (`401 refreshes once then retries`).
4. **The gabbai's list is a real Excel export.** That means a CSV in windows-1255 or with a UTF-8 BOM,
   Hebrew headers, blank lines, emails with mixed case, or the same email twice → the names decode
   correctly, emails are lower-cased and de-duplicated, and bad rows are reported by row number and never
   echoed. Task 17 (`decodes windows-1255`, `dedupes case-insensitively`) and Task 2
   (`test_reimport_is_idempotent`).
5. **Someone opens an invite link while signed out** and goes through register → email code → sign-in →
   profile → the invite is still accepted at the end. It is not lost on the way, and it is not accepted
   twice. Task 11 (`pending invite survives the sign-up detour`).

**Interfaces:**
- Produces (the app's types in Task 7 mirror these exactly):
  - `POST /v1/kehilot/{k}/invites` takes `{uses?, days?, role?: "listener"|"member", classification?: ""|"א"|"קבוע"}`.
    - `role` defaults to `listener`.
    - `role: "member"` needs a gabbai; a member who sends it gets 403 `forbidden`.
    - `classification` is accepted only with `member`; otherwise 400 `invalid_classification`.
    - Other bad values get 400 `invalid_role`.
  - `create_invite(k, inviter_id, role, uses, days, classification='')` stores `classification`.
  - `GET /v1/invites/{code}` → 200 `{kehilaName, role, expiresAt}`.
  - `accept_invite(code, user_id, display_name, now, broadcast_default)`:
    - A `member` invite sets the classification from the invite, `canBroadcast = broadcast_default`, and
      deletes any `REQ#<user>`.
    - When the caller is already a `listener` and the invite role is `member`, one transaction upgrades the
      membership (condition `#r = :listener`), consumes a use and deletes the request. The response is
      200 `{kehilaId, role: "member"}`.
    - Every other existing membership still gets 409 `already_member`.
  - `GET /v1/kehilot/{k}` adds:
    - `canBroadcast: bool`;
    - `pendingRequest: bool` (a `REQ#<caller>` item exists);
    - `notify: {mutedChannels: [], mutedTypes: [], membersBroadcasts: "all"|"management_only", mutedMembers: []}`,
      with these defaults filled in.
  - Message objects from `GET .../messages` and `GET .../messages/{m}` add `read: bool` for the caller. The
    flags come from `repo.read_flags(k, user_id, message_ids) -> set[str]`, one `BatchGetItem` of up to 50
    `READ#` keys. Feed items do not carry `read`; the `read` change kind covers it.
  - `GET /v1/kehilot/{k}/members` (member or gabbai; a listener gets 403) → `[{userId, displayName}]` for
    roles `member` and `gabbai`, sorted by `displayName`. The compose screen uses it to pick a target family.

### Task 2: Backend: list import (pre-created accounts)

**Files:**
- Create:
  - `server/cloud/accounts.py`
  - `server/cloud/importer.py`
  - `server/tests/cloud/test_import.py`
- Modify:
  - `server/cloud/inputs.py` (`body_object(ctx, limit=MAX_BODY_BYTES)`)
  - `server/cloud/routes_admin.py`
  - `server/cloud/handler.py`
  - `server/cloud/repo_members.py`
  - `server/API.md`

**Interfaces:**
- Produces:
  - `accounts.ensure_account(client, pool_id, email) -> tuple[str, bool]` returns `(sub, created)`.
    - First it calls `AdminGetUser(Username=email)`. The pool uses `username_attributes = ["email"]`, so
      the email works as the username.
    - When the user is not found, it calls
      `AdminCreateUser(Username=email, UserAttributes=[email, email_verified="true"], MessageAction="SUPPRESS")`,
      then `AdminSetUserPassword(Password=<random>, Permanent=True)`.
    - The random password comes from `secrets.token_urlsafe(32)` plus `"aA1!"`. It is never stored,
      returned or logged.
    - On `UsernameExistsException` (a race) it reads the user again.
  - `importer.import_rows(repo, client, pool_id, k, rows) -> list[dict]`. Each result is
    `{index, status, error?}`:
    - `status` is one of `created`, `added`, `upgraded`, `exists`, `invalid`;
    - `error` is one of `invalid_email`, `invalid_first_name`, `invalid_last_name`, `invalid_role`,
      `invalid_classification`, `duplicate_email`.
    - Results carry no names or emails.
    - Emails are stripped and lower-cased. They must match `^[^@\s]+@[^@\s]+\.[^@\s]+$` and be at most 254
      characters.
    - For each valid row:
      1. `ensure_account`.
      2. `repo.create_user_id(sub, new_id())`. It is idempotent and returns the stored `userId`.
      3. `repo.put_profile_if_absent(user_id, first, last, lang)`. `lang` is the Kehila's
         `settings.defaultLang`.
      4. `repo.import_membership(k, user_id, display_name, role, classification, broadcast_default)`, which
         returns `added`, `upgraded` or `exists`:
         - with no membership, a conditional put → `added`;
         - a `listener` membership with a row role of `member` or `gabbai` → an update with
           `#r = :listener`, and the `REQ#` is deleted → `upgraded`;
         - any other existing membership is left as it is → `exists`.
    - `created` replaces `added` when `ensure_account` made a new Cognito user.
  - `POST /v1/kehilot/{k}/admin/import` (gabbai) with
    `{rows: [{firstName, lastName, email, role: "listener"|"member"|"gabbai", classification: ""|"א"|"קבוע"}]}`:
    - 1 to 25 rows, body limit 64 KB;
    - 200 `{results: [...]}`;
    - 400 `invalid_rows`.
    - The client batches longer lists (Task 17).
    - The handler logs only the counts per status.

### Task 3: Backend: Cognito triggers (account linking and he/en emails)

**Files:**
- Create: `server/cloud/cognito_triggers.py`, `server/tests/cloud/test_cognito_triggers.py`
- Modify: `tools/build_lambda.py` (only if the handler list is explicit)

**Interfaces:**
- Consumes: `accounts.ensure_account` (Task 2).
- Produces: `cognito_triggers.handler(event, context, client=None) -> event`, dispatched on
  `event["triggerSource"]`:
  - **`PreSignUp_ExternalProvider`** (a first Google or Apple sign-in):
    1. Read `event.userName`. It is `Google_<id>` or `SignInWithApple_<id>`; split it at the first `_`.
       Map the provider name with `{"google": "Google", "signinwithapple": "SignInWithApple"}`, matching
       case-insensitively.
    2. Check the email. If it is missing → raise `Exception("email_required")`. For Google, if
       `email_verified != "true"` → raise `Exception("email_unverified")`. (Apple emails, relay addresses
       included, are verified.)
    3. Find a native user (status not `EXTERNAL_PROVIDER`) with `ListUsers(Filter='email = "<email>"')`.
       If there is none, create one with `accounts.ensure_account`.
    4. Call `AdminLinkProviderForUser(DestinationUser={ProviderName: "Cognito", ProviderAttributeValue: <native username>}, SourceUser={ProviderName, ProviderAttributeName: "Cognito_Subject", ProviderAttributeValue: <id>})`.
    5. Return the event.

    The result is one account per email. The token's `sub` is the native user's, so the `userId` and the
    memberships carry over.
  - **`PreSignUp_SignUp` and `PreSignUp_AdminCreateUser`:** return the event unchanged.
  - **`CustomMessage_SignUp`, `CustomMessage_ResendCode` and `CustomMessage_ForgotPassword`:** set
    `response.emailSubject` and `response.emailMessage` from `EMAIL_TEXT[source][lang]`.
    - `lang` comes from `event.request.clientMetadata.lang`. When it is not `he` or `en`, use `he`.
    - The message contains `event.request.codeParameter` (`{####}`).
    - Hebrew text: "קוד האימות שלך לקהילות: {####}" and "קוד לאיפוס הסיסמה בקהילות: {####}".
    - English text: "Your Kehilot verification code: {####}" and "Your Kehilot password reset code: {####}".
  - **Any other source:** return the event unchanged.
  - Log only the trigger source and the outcome (`linked`, `created_and_linked`, `passthrough`).
